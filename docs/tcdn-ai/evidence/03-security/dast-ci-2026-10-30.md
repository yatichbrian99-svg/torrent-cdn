## Both passes really authenticated?

The first attempt claimed an authenticated pass and **was not one**: ZAP's Replacer rule
(`-config replacer.full_list(0)…`) did not apply the bearer header, and 46 requests to `/auth/me`
answered 401. That is why the pass now goes through `auth_proxy.py` and why the workflow has a
proof step that fails the job. Recorded from this run:

```
baseline: 46 /auth/me requests in the log, 1 answered 200 (expected 0 while unauthenticated)
after the authenticated pass: 68 /auth/me requests in the log, 3 answered 200 (baseline 1)
authenticated coverage proven: 2 request(s) to a JWT-only route answered 200 with the injected token
```

The remaining 401s are the unauthenticated pass and the scanner's own credential-bypass probes,
which is expected. The first proxy run also fired `POST /auth/logout` (it is in the spec), revoking
the seeded session mid-scan; logout is now out of scope for the authenticated pass only.

### The MEDIUM is a real defect, not a false positive

`Coordinator.heartbeat` validates the inner payload *after* the envelope
(`HeartbeatPayload(**envelope.payload)`, `backend/app/ai/service.py:1063`) instead of at the request
boundary, so a well-formed envelope carrying a hostile payload raises inside the handler. The
proxy tally counted **156 × 500** on `POST /api/ai/v1/nodes/heartbeat` in this run (163 in the run
before it) on a route whose only authentication is a signature — an unauthenticated caller can
provoke 500s with attacker-controlled input. ZAP's 30002 alert fires on the same path for the same
reason. **Not fixed in this branch**; it is the first item in "Next actions" in
`PUSH_CHECKLIST.md`.

## What this does not prove

- **No HTML surface.** The frontend and Caddy are not in the scan. A JSON API gives the passive
  rules little to inspect, so five alert types is a weak result — it is not evidence of absence.
- The active scan is bounded (6 minutes, 1 minute per rule) against a throwaway stack, so timing-
  or state-dependent issues may not appear.
- Most of `/api/ai/v1/*` needs an API key; it was scanned as an unauthenticated caller plus the
  scanner's credential probes, not as a customer.
- **There is no hosted staging deployment.** This is a CI stack that mirrors the staging
  blueprint's gates, not the Render service, and `render.staging.yaml` has still never been applied.
