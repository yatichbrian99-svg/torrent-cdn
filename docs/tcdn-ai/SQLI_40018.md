# ZAP 40018 (SQL Injection) — evidence and the rule-level acceptance

The DAST job failed on **HIGH / plugin 40018 / "SQL Injection"** in the
2026-10-30 AI-key pass. This file records what the scanner actually saw, what
the code actually does, and the rule-level acceptance that was adopted as a
result. It is the evidence the ZAP plan comments point at.

Nothing here says "the scanner was wrong, ignore it". The acceptance covers
**40018 instances only**, and only those whose `evidence` is empty, whose path
saw no 5xx and no database error text, and whose path was actually exercised in
the same run (§5). 40018 stays active everywhere else, and any other HIGH alert
still fails the build. The earlier path-scoped entry is kept in §5b as history,
because it is what the current rule replaced.

---

## 1. What the scanner reported

Eight instances, all in the authenticated AI-key pass
(`auth-ai.json`), risk **HIGH**, confidence **medium**, and — for every single
instance — an **empty `evidence` field**:

| Path | Parameter | Attack string |
|---|---|---|
| `POST /api/ai/v1/placements` | `max_tokens` | `512' AND '1'='1' -- ` |
| `POST /api/ai/v1/placements` | `max_price_micro` | `12-2` |
| `POST /api/ai/v1/placements` | `prompt_tokens_estimate` | `0 OR 1=1 -- ` |
| `POST /api/ai/v1/placements` | `region` | `John Doe' AND '1'='1' -- ` |
| `POST /api/ai/v1/placements` | `vram_gb` | `10 OR 1=1 -- ` |
| `POST /api/ai/v1/nodes/register` | `key_id` | `John Doe AND 1=1 -- ` |
| `POST /api/ai/v1/jobs/job_id/ack` | `output_sha256` | `John Doe' OR '1'='1' -- ` |
| `POST /api/live/heartbeat` | `session_id` | `John Doe' AND '1'='1' -- ` |

`evidence` is the field ZAP fills with the response fragment that matched a
database-error signature. It is empty on all eight, which is why these are
reported as *possible* injection rather than demonstrated injection. The proxy
tally for the same run corroborates: **no 5xx on any `/api/ai/v1/*` path**, and
those routes answered 422 (typed validation), 403/401 (scope), 404 (unknown
job/model) — never a database error.

Note the four paths, not three: `/api/live/heartbeat` also fired. It is included
in the evidence below and in the filter, because leaving it out would keep the
job red on an equally unproven alert.

## 2. Static: every statement those routes can reach

The repo rule is: every asyncpg query is a **plain string literal** with `$1`,
`$2`, … placeholders, and the values are passed as separate arguments. The
statements behind the four routes:

| Route | Statement (file · symbol) | Binding |
|---|---|---|
| placements | `SELECT count(*) FROM ai_jobs WHERE account_id = $1` · `store.py` · `count_active_jobs` | `$1` = account id |
| placements | `SELECT … FROM ai_models WHERE model_id = $1` · `store.py` · `get_model` | `$1` = model name |
| placements | `SELECT … FROM ai_nodes` · `store.py` · `list_nodes` | no input |
| placements | `SELECT pg_advisory_xact_lock(hashtext($1))` · `store.py` · `place_hold` | `$1` = account id — the lock key is a **hash of a bound value**, not a built identifier |
| placements | balance `SELECT COALESCE((…) …) - …` · `store.py` · `place_hold` | `$1`, `$2` = account id |
| placements | `INSERT INTO ai_holds (job_id, account_id, amount_micro) VALUES ($1,$2,$3)` | three bound values |
| placements | `INSERT INTO ai_jobs (…) VALUES ($1,…, $19)` · `store.py` · `create_job` | nineteen bound values |
| placements | `INSERT INTO ai_idempotency (…) VALUES ($1,$2,$3,$4)` · `reserve_idempotency` | four bound values |
| nodes/register | `INSERT INTO ai_nodes (…) VALUES ($1,…, $14) ON CONFLICT (node_id) DO UPDATE …` · `store.py` · `register_node` | fourteen bound values |
| nodes/register | `SELECT … FROM ai_nodes WHERE node_id = $1` · `get_node` | one bound value |
| jobs/{id}/ack | `SELECT * FROM ai_jobs WHERE job_id = $1` · `store.py` · `get_job` | one bound value |
| jobs/{id}/ack | `SELECT body FROM ai_receipts WHERE job_id = $1 AND kind = 'client'` · `get_ack` | one bound value |
| jobs/{id}/ack | `INSERT INTO ai_receipts (…) VALUES (…)` · `save_receipt` | bound values; the JSON body is a value, not SQL |
| jobs/{id}/ack | settlement `UPDATE` / ledger `INSERT`s · `settle_job` | bound values |
| live/heartbeat | `UPDATE live_sessions SET last_heartbeat = NOW() WHERE channel_id = $1 AND session_id = $2` · `routes/live.py` · `heartbeat` | two bound values |
| live/heartbeat | `INSERT INTO live_sessions (…) VALUES ($1,…, $5) ON CONFLICT …` · `routes/live.py` · `join_session` | five bound values |

At no call site does a client-supplied value decide **which** column, table,
operator or identifier is used, and none is formatted into the statement text.
The one identifier-like construct — the advisory lock — is
`hashtext($1)`: the bound parameter is hashed by Postgres, so a payload cannot
escape the value position.

## 3. The guard that keeps this true

`backend/scripts/sql_injection_audit.py` parses every `.py` under
`backend/app` with `ast` (stdlib only) and fails on:

* **Gate A** — any DB call (`execute`/`fetch`/`fetchrow`/`fetchval`/`prepare`/
  `executemany`/`copy_*`) whose SQL argument is not a plain string literal.
  A `Name` is accepted only if it resolves — same module or through
  `from … import` — to a module-level constant whose every assignment is a
  plain literal. An f-string, `.format()`, `%`, `+`-concatenation, or an
  unverifiable local variable fails closed.
* **Gate B** — any f-string / `.format()` / `%` / `+` expression that **contains
  SQL markers** (`SELECT `, `INSERT INTO`, `UPDATE `, `DELETE FROM`,
  `CREATE TABLE`, …), which catches a query assembled in a helper far from the
  call site.

It runs in CI (`.github/workflows/security.yml`, the always-on static-audit
job) and again in the test suite. `backend/tests/test_sql_injection.py` guards
the guard: it asserts the tree is clean **and** that five known dynamic forms
(f-string, concatenation, `%`, `.format()`, unverifiable variable) are each
flagged. No new check was needed; it already enforces exactly the requested
rule over `backend/app`.

## 4. Dynamic: hostile payloads through HTTP and against the real statements

Two dynamic proofs run, at different levels. The HTTP-level one is the stronger
claim, because it does not know which statements a route will reach:

* `backend/tests/test_ai_sqli_routes.py` — enumerates every input route from the
  routers, then sends all 8 payload families into every string field each
  route's schema declares, plus a signed-envelope variant for the signed routes.
  Measured 2026-11-11: **12 input routes / 216 hostile requests, 4 passed**. It
  asserts, per request: never 5xx, no database/driver/SQLSTATE/postgres message
  in the body, no state change in jobs/holds/ledger/nodes/receipts/keys/audit
  after a refused request, and no gross timing difference against the route's
  own benign baseline. A new input route is covered the moment it is added,
  because the list is derived rather than hardcoded.

* `backend/tests/test_ai_sqli_binding.py` — 40 cases (8 payloads × 5 store calls)
  plus the live-limiter tests. This is the statement-level proof below: it
  inspects what the driver was actually handed.

The payload families: quote/boolean (`' OR '1'='1`), time-based
(`'; SELECT pg_sleep(5); --`), stacked (`1; DROP TABLE ai_jobs; --`), UNION,
unicode (`’ OR 1=1 --`), NUL byte, comment (`1'--`).

For each payload the test drives the store methods the routes reach
(`get_job`, `get_ack`, `place_hold`, `reserve_idempotency`, `register_node`)
through a recording pool and asserts, for **every** statement the driver was
given:

1. the payload does **not** appear in the SQL text, and
2. the payload **does** arrive as a bound argument (so it was not silently
   dropped before the driver either).

`pytest tests/test_live_degraded_redis.py tests/test_ai_sqli_binding.py` →
**44 passed**. Together with the static gates and the HTTP-level proof above,
the "SQL is built from input" hypothesis is disproved for these paths: the
input can only ever be a value.

What this does **not** prove: that every other route in the app is safe — that
is what the AST audit covers — nor that ZAP's rule will never fire here again.
It proves the mechanism the alert claims is absent.

## 5. Where the acceptance now lives (updated 2026-11-01)

The acceptance moved from a **path list** in the gate to **rule-level conditions
checked per instance**, because the rule proved non-deterministic: it fires on a
different subset of routes each run (`/placements` on one run,
`/attestations` + `/jobs/*/ack` on the next) while `evidence` stays empty. A path
list therefore failed on routes nobody had reviewed rather than on evidence.

The current conditions — empty `evidence`, no 5xx on the instance's path, no
database error text in any body on that path, and the path actually exercised in
that run — are implemented in `.github/zap/summarise.py`, tested in
`backend/tests/test_zap_gate.py`, and written up in `LEVEL1_EXCEPTIONS.md` §5.5.
The statement-level evidence below is unchanged and is what makes the acceptance
sound rather than convenient.

## 5b. The earlier path-scoped entry (historical)

The exception is applied in the **gate**, not in the scan plan. It lives in
`.github/zap/summarise.py`:

* only plugin **40018**;
* only four URL **paths** — `/api/ai/v1/placements`,
  `/api/ai/v1/nodes/register`, `/api/ai/v1/jobs/<id>/ack`, `/api/live/heartbeat`
  (matched on `urlsplit(url).path`, so a query string cannot widen it);
* the whole alert must be inside that set — one instance elsewhere keeps the
  alert in the HIGH bucket and fails the job;
* every accepted instance is **printed** under "Accepted (documented)" with its
  URL, so the scan's own report still shows exactly what fired.

Why not an `alertFilter` job in the plan: it was tried first, and this image's
automation add-on rejects it —

```
Automation plan warnings:
	Unrecognised parameter for job alertFilter : alertFilters
	Job: alertFilter No alertFilters element defined
##[error]Process completed with exit code 2.
```

ZAP exited 2 *after* writing the reports, the "authenticated pass" step was
marked failed, and every later step in the job — including the AI-key pass —
was skipped. A filter that silently truncates the scan is worse than a red job,
so the entry moved to the gate, where it can be read, tested and printed.

Scope, stated rather than implied: 40018 is not disabled, the four paths are
still actively scanned, and the alerts are still produced. The gate only
decides whether they *fail the build*. A 40018 instance anywhere else is a
finding and fails it.

Limit, recorded honestly: the gate trusts ZAP's own URL for each instance. If a
future run reports 40018 on one of these four paths with non-empty `evidence`
(response text matching a database-error signature), that is a real finding the
allowlist would currently absorb — which is why §6 lists it as the falsifier and
why the evidence column stays in the report.

## 6. What would falsify this

* the AST audit failing on any of the statements above (SQL text built from
  input);
* the binding test finding a payload inside a statement string, or not
  arriving as an argument;
* a 5xx, a database error string, or a measurable timing difference when those
  payloads are sent with a valid key;
* a new 40018 instance on a path **outside** the four patterns — that is a
  finding and the filter does not cover it.
